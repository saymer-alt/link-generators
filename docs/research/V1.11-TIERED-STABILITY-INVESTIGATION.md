## Подтверждённые дефекты harness

- `until` подавлял исключения, не сохранял ответ, код соединения и состояние core.
- H создавал `s2` без stop/finally. Последующие сценарии выполнялись с лишним core;
  успешный `process.exit(0)` не завершает независимый дочерний процесс.
- Failure/watchdog завершали Node без общей очистки mocks/health/restart core.
- Listen Promise не отвергал bind error; core logs были неограниченными.
- **RUNTIME-PROVEN, Windows:** TCP-only `freePort` выбрал mixed-port 54117,
  входящий в UDP exclusion 54064–54163. Core сохранил живой controller и ROOT=T1,
  но сообщил `listen udp ... bind ... forbidden by its access permissions` и не
  поднял mixed listener. Независимый UDP bind дал EACCES; TCP exclusion list этот
  диапазон не содержит. Отказ случился в H контролируемого late-health run,
  не в исходном Linux A. Его JSON и FAIL сохранены. `freeMixed` теперь резервирует
  и проверяет UDP+TCP на одном loopback-порту, затем освобождает их перед spawn.
  Unit regression доказывает, что TCP-only accepts UDP-occupied port, dual rejects.
- Первая dual-protocol реализация корректно отвергала занятый TCP candidate, но
  не выбирала следующий. Это внесённый в ходе расследования allocator defect:
  Linux31 run37959310823 sample7 получил UDP candidate36191, занятый своим TCP health
  server, и завершился EADDRINUSE в H после успешных A–D. Результат **9/10**, не10/10.
  Окончательный allocator ограничен8 candidate attempts **до spawn**; EADDRINUSE/EACCES
  фиксируются в timeline, остальные ошибки немедленно возвращаются. Core, traffic
  или failed suite не перезапускаются. Детерминированная реальная TCP occupancy probe
  подтвердила reject первого candidate и выбор второго при сохранении health listener.

Утечка H происходит **после** A и не объясняет исходное падение A внутри того же запуска.
Изменения ограничены наблюдением и lifecycle test infrastructure, без изменения генератора,
YAML semantics, ожиданий priority/partial/failover/failback и бюджета A.

## Воспроизведение

`MIHOMO_BIN`, `JS_YAML_PATH` должны указывать на проверенный core и js-yaml 4.1.0.
`node tools/tiered-stability/repeat.cjs 20 <output-directory>` выполняет независимые
запуски с новыми каталогами/процессами/портами. Failures считаются и не повторяются.
Сохраняются JSON per run, bounded core tail, timeline, HTTP responses/errors,
health observations, counters и проверка закрытия core/controller/mixed ports.
Отдельный ограниченный CI workflow запускает 10 samples/version и сохраняет artifacts
даже при failure. Он не добавляет повторов к неуспешному Generator CI job.

Controller GET snapshots не запускают delay/health probes; `/version`, mixed readiness,
ROOT selection, mock health и фактический T1 response фиксируются отдельно.
Выборочная диагностика добавляет небольшую стоимость наблюдения; это не побитовая
реплика первоначального execution timing.

## Первичные выводы о причинах

- `last=false` исходного A доказывает минимум один завершённый predicate с body,
  отличным от T1A/T1B. Одни только исключения всех запросов оставили бы `last=undefined`.
  Позднейшие исключения могли подавляться; HTTP status/body неизвестны.
- Прямой причинный переход от утечки H к предшествующему A того же run исключён.
- Windows UDP exclusion даёт другой signature: mixed ECONNREFUSED и last=undefined.
  Нельзя объявлять это причиной исходного Linux last=false.
- Late-health probe на 31: actual T1 до первого успешного health check,
  ROOT=T1 и leaf alive=true при пустой history; ответы health задержаны на 800 ms
  сверх health timeout 500 ms. `alive=true` и выбор группы не доказывают completed health.
- Небольшое различие latency версий в выборке не доказывает version regression.

Продуктовые index/runtime/YAML semantics не изменены. ROOT CAUSE UNKNOWN сохраняется.

## Воспроизводимый механизм health starvation (не attribution original CI)

`node tools/tiered-health-order.cjs fieldtest-private/health-order` в isolated worktree:
три recovery probes и один persistent probe, свежие process/ports/temp/mocks каждый раз.
Меняются только T1 HEAD health response delay800ms и controller polling delay900ms.
Data responses сохраняют5ms, health timeout500ms и A budget15000ms неизменны.

На обеих версиях recovery3/3: initial ROOT=T2, T1A/T1B alive=false, первый actual
response T2A, затем actual T1 примерно2.2s от spawn. Persistent probe на обеих
версиях даёт **A: traffic via T1: last=false** при ROOT=T2, healthy T2 и постоянных
T1 health timeouts. Повторная проверка экспортированного runner дала тот же результат.
Expected failures проверяются как failures, а не объявляются успешным Tiered contract.
Все cores/ports/sockets очищены.

Это доказывает, что health starvation может породить старую строку ошибки без
version regression и без нарушения fallback semantics (T1 признан dead по health).
Original mocks имели5ms delay; нет доказательства, что их T1 health requests реально
превышали500ms в исходном CI, тем более на всём15s интервале. Поэтому original
root cause не повышается до LIKELY/CONFIRMED.

## Verdict и границы

**Original ROOT CAUSE UNKNOWN.** Tested conditions не воспроизвели original A signature
на неизменённой здоровой конфигурации. No confirmed generator/Mihomo version regression.
Не исключены rare startup/health ordering race, nested fallback state, runner contention,
port handoff race после release reservation и неизвестный initial HTTP error response.
Чистые normal samples не дают основания объявить эти гипотезы невозможными.
Host variant PASS на обеих версиях тоже не исключает редкую metadata-dependent ошибку.
Искусственные ROOT=T2 и unexpected-body faults оба дали бы старую сигнатуру
`A: traffic via T1: last=false`; одинаковая строка ошибки не идентифицирует причину.

READY FOR OWNER UI TEST: YES. READY FOR STABLE PROMOTION / RELEASE: NO.
Владелец должен оценить сохранённую неопределённость, выполнить UI/device acceptance
и дать отдельное production GO. Real WG/AWG, owner VPS/Keenetic, TUN, system DNS/routes/
firewall, публичные test endpoints, UDP payload routing не запускались и не изменялись.
Stable447af225, v1.10.0 tag и release защищены; #120 вне scope.
Final merged main SHA и его CI фиксируются в итоговом handoff после merge PR224.
