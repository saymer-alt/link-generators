# WARPSCOUT 0.16.1 — полевые результаты двух VPS, 6 ноября 2026 года

> **Статус:** реальные результаты из SSH-вывода владельца, без передачи/публикации приватных ключей. Это снимок на конкретную дату, **не постоянные характеристики Cloudflare IP** и не свидетельство работы итогового маршрута через Mihomo. Основная инструкция: [WARPSCOUT на VPS](../WARPSCOUT-VPS.md).

## Зачем сохранить

В один день были проверены два VPS с разной видимой географией WARP и скоростями. Получены готовые для локального импорта конфиги WG, MASQUE H2 и H3. Практически полезны: различие между `NODE` и `SEEN AS`, отсутствие гарантии эффективности NODE-фильтра, необычный **H2/TCP endpoint с портом 500**, сравнение скоростей протоколов, два **неидентичных файла** WARP-аккаунта на одном VPS и безопасное обновление уже установленного бинарника.

Все имена файлов относятся к **локальным файлам на VPS**, а не к объектам в GitHub. Их содержимое (включая приватные ключи и токены) **не коммитить**.

## 1. Saymer2: Debian 12, шведский VPS

- Архитектура: `amd64`; установленный ранее бинарник `/root/.local/bin/warpscout` версии `0.16.0`.
- Обновление до `0.16.1` выполнено **в том же каталоге** через `INSTALL_DIR=/root/.local/bin sh install.sh --yes`; второй запуск установщика показал `warpscout 0.16.1 is already installed`.
- Повторно использован `/root/warpscout-data/warpscout-account.json`, регистрация не потребовалась.
- Скан WG с `-exclude-node ARN` и повторный с `-n 20 -exclude-node ARN` вернули `every endpoint was excluded by node ARN`. Эти фильтры **только отбрасывают результаты**; они не меняют маршрутизацию anycast Cloudflare.

После обновления выполнены `-P -jt 10 -speed -best-by speed`-сканы:

Локальные файлы: `wg-best.conf`, `h2-best.yaml`, `h3-best.yaml` и одноимённые `*-report.txt`. Просмотренный несекретный вывод H2/H3 подтвердил SNI `consumer-masque.cloudflareclient.com`; у H2 присутствовал `network: h2`, у H3 — нет.

## 2. hungry-boyd: Ubuntu 24.04.5 LTS, другой VPS

- Linux `x86_64`; бинарник `/usr/local/bin/warpscout` **уже** был версии `0.16.1`, **обновление в этой сессии не требовалось и не выполнялось**.
- Найдены **два** файла аккаунта: `/root/warpscout-account.json` и `/root/warpscout-data/warpscout-account.json`.
- `cmp -s` показал, что файлы **байтово не идентичны**. Этого недостаточно, чтобы утверждать, что они представляют разные логические аккаунты (различаться могут и форматирование/поля). Не перезаписывать, не удалять, не пересоздавать и не публиковать ни один файл без отдельной проверки.
- Сканирование из `/root/warpscout-data` подтвердило `Using cached WARP account from warpscout-account.json`, то есть использовался **именно файл из рабочего каталога**. Получены три успешных скана.
- В рабочем каталоге до новых тестов уже лежали датированные отчёты от 23 сентября 2026 года; новая серия использовала новые имена, не перезаписав старые.

### Особые выводы для генератора

1. **H2 на порту 500 — настоящий измеренный результат** в этом прогоне: `162.159.199.106:500` по **TCP/H2**, а не WireGuard/UDP. Не заменяйте его без причины на `443` при интерпретации скана. Однако в отдельных клиентских сетях такой TCP-порт может быть недоступен: проверенный `162.159.198.187:443` — резерв.
2. Генератор имеет встроенный режим **H2 Safe Ports Only** для случаев, когда точный endpoint не импортирован. При загрузке **WARPSCOUT/Mihomo YAML с `proxies:`, `type: masque`** парсер должен распознать H2/`network: h2`, SNI и явный `server:port` и дать **импортированному** endpoint приоритет над Safe Ports. При ручном вводе произвольных полей тот же приоритет **не следует предполагать**: после Build необходимо проверить итоговый `server` и `port` в сгенерированном YAML.
3. **H3:** `162.159.198.2:8095` — QUIC/UDP; не ставить `network: h2`. H2 — TCP/HTTP2, H3 — QUIC/HTTP3; поле `udp: true` само по себе не переводит H2 в H3.
4. Штатный SNI WARPSCOUT/MASQUE для ручного заполнения — `consumer-masque.cloudflareclient.com`. **На hungry-boyd содержимое сохранённых YAML в переписке не выводилось**, поэтому это ожидаемое штатное значение, а не независимо подтверждённое извлечение из этих конкретных файлов. Перед ручной сборкой сравнить SNI с локальным YAML.
5. Для WG использовать свой действующий `PrivateKey`, соответствующий серверный `PublicKey` и внутренний IP WARP. **Не смешивать identity разных аккаунтов и не публиковать ключи**. Сами endpoint'ы — публичные адреса, не секреты.

## 3. Сравнение двух сетей — что действительно следует из измерений

| Показатель | Saymer2 (шведский VPS) | hungry-boyd (другой VPS) |
|---|---|---|
| WG | 396.0 Мбит/с | 206.2 Мбит/с |
| MASQUE H2 | 74.1 Мбит/с | 154.6 Мбит/с |
| MASQUE H3 | 166.2 Мбит/с | 134.8 Мбит/с |
| TUN PING победителей | 1 мс | 10 мс |
| Cloudflare NODE | ARN | ARN |
| SEEN AS | SE | EE |
| Место H2/H3 по скорости | H3 быстрее H2 | H2 быстрее H3 |

**Следствие:** нельзя рекомендовать H3 «всегда быстрее H2», даже если все endpoints ведут на один NODE. На `hungry-boyd` H2 оказался быстрее H3, на `Saymer2` — наоборот. WG был быстрее в обоих замерах, но сравнение **однопоточное и только среди предварительно выбранных WARPSCOUT кандидатов**. Это не тест пропускной способности клиента через готовый Mihomo, не замер длительной стабильности и не показатель доступности этих портов из иной сети.

Выбор NODE/SEEN AS зависит от BGP/peering, периода измерения, доступности Cloudflare; конкретный IP:port не фиксирует colo навсегда. В обоих проверенных сценариях NODE был ARN; на Saymer2 исключение ARN не дало альтернативы. Это не делает фильтр «сломавшимся».

## 4. Что проверить при следующем визите (без лишних тестов)

- Убедиться, что используется старый бинарник в правильном каталоге (`/usr/local/bin` у `hungry-boyd`, `/root/.local/bin` у `Saymer2`), а не дубликат из `PATH`; обновлять при появлении новой upstream-версии.
- Найти фактический каталог `warpscout-account.json`, **не трогать** другой файл без отдельного анализа. Не регистрироваться заново без необходимости.
- Повторять `-P -speed -best-by speed` с датированными `-o`/`-conf` и сверять `NODE`, `SEEN AS`, `LOSS`, `TUN PING`, скорость. Для новых значений делать **новый датированный снимок**, а не переписывать эти полевые результаты.
- Проверить, сохранил ли генератор точные H2 `162.159.199.106:500` и H3 `162.159.198.2:8095` после импорта **своих локальных файлов**, и проверить выход на целевом устройстве. **Полевая приёмка маршрута через Mihomo не проводилась**.
- При необходимости изолированно перепроверить стабильность, доступность нужных TCP/UDP-портов с клиентской стороны и поведение приложений; не объявлять успех лишь по скану WARPSCOUT.

Никаких SSH-сессий или файлов серверов в этот GitHub-коммит не переносилось; все цифры и имена — из опубликованного пользователем вывода без ключей.
