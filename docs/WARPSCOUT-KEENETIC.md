# WARPSCOUT на Keenetic: ищем рабочий AWG с Cloudflare-узлом не в РФ

> **Главная задача:** прямо на роутере Keenetic/Netcraze найти **работающий AmneziaWG (AWG) endpoint WARP**, у которого **Cloudflare NODE / colo расположен за пределами России**, проверить потери и задержку, сохранить готовый конфиг.
>
> На фильтрованных подключениях **обычный WireGuard (WG) пропускаем полностью**: он может видеть доступные UDP-порты, но так и не установить рабочий туннель. **Сканируем только AmneziaWG (AWG)**. MASQUE H2/H3 оставлены как необязательные эксперименты в самом конце.
>
> **Важно:** зарубежный Cloudflare NODE и страна **выходного IP / `SEEN AS` — разные вещи**. В наших дачных испытаниях 2026-09-25 узлы `ARN`, `FRA`, `AMS` находились вне РФ, но `SEEN AS` оставался `RU`. Эта инструкция подбирает **иностранный colo**, а не обещает зарубежную GeoIP-страну для сайта.

## Быстрый маршрут для новичка

Идите **по порядку**: **1. установка → 2. проверка аккаунта → 3. AWG-скан с исключением российских узлов → 4. проверка результата → 5. сохранённый конфиг**. Дальнейшие разделы нужны только при проблемах или специальных требованиях. **Не запускайте предварительный WG baseline.**

**Уже установили WARPSCOUT и зарегистрировали WARP?** Сразу выполняйте в SSH следующую последовательность (повторная установка и WG-тест не нужны):

~~~sh
cd /opt/etc/warpscout
warpscout scan -p awg -P -jt 4 -gen-i1 quic -exclude-country RU -o awg-non-ru-report.txt -conf warp-awg-non-ru.conf
~~~

Это та же основная команда, что и в шаге 3. Если ранее `wg` завершился `no working endpoints found - try -p awg -gen-i1 quic`, **сразу переходите к AWG**, не повторяя WG-скан.

Все команды для запуска скана **самодостаточны**, содержат `-jt 4`. Переменные `JT` и `"$JT"` не используются. После повторного SSH-подключения достаточно снова перейти в каталог командой `cd /opt/etc/warpscout`.

В итоге ожидаем **два файла**:

- `awg-non-ru-report.txt` — результаты скана;
- `warp-awg-non-ru.conf` — готовая конфигурация AWG с лучшим endpoint'ом **среди прошедших фильтр non-RU NODE**, если такие нашлись.

## 0. Что необходимо

- Роутер Keenetic/Netcraze с интернетом и **установленным, запущенным Entware**, доступ по SSH.
- Свободное место в `/opt`, запас памяти и работающий DNS/интернет на самом роутере. Ограничим параллельные туннели до четырёх, чтобы не перегружать маломощные модели.
- Не путайте WARPSCOUT и VPN-клиент: WARPSCOUT **проверяет** endpoint и генерирует конфиг, но **не переводит весь трафик роутера** в туннель автоматически.

Вводите команды в **SSH-консоли роутера**, не в CMD Windows. Не публикуйте приватные файлы регистрации и конфигурации.

## 1. Устанавливаем WARPSCOUT

Скопируйте и выполните **одну строку** целиком:

~~~sh
opkg update && opkg install curl ca-bundle && curl -fSsL https://raw.githubusercontent.com/saymer-alt/entware-go/gh-action-build/warpscout/install.sh | sh
~~~

В конце успешной установки должны появиться сообщения вида:

~~~text
WARPSCOUT 0.16.0 is ready
WARPSCOUT installation complete.
~~~

Версия может быть новее. Промежуточное `Unknown package 'warpscout'` допускается, **если** установщик затем успешно загрузил IPK из GitHub и сообщил об окончании установки.

Установщик может зарегистрировать WARP-аккаунт сам. Даже если `API unreachable directly` или relay не ответил, не делайте вывод об ошибке до **финального сообщения**. `Registered fresh WARP account` означает, что регистрация состоялась.

## 2. Подготавливаем каталог и проверяем аккаунт

Выполните **последовательно**:

~~~sh
mkdir -p /opt/etc/warpscout
~~~

~~~sh
cd /opt/etc/warpscout
~~~

~~~sh
warpscout version
~~~

~~~sh
ls -lh /opt/etc/warpscout/warpscout-account.json
~~~

**Если файл аккаунта существует и не пустой**, всё готово: переходите к шагу 3.

**Только если файл отсутствует**, зарегистрируйте аккаунт вручную:

~~~sh
cd /opt/etc/warpscout
warpscout register
~~~

Повторите проверку файла командой `ls`. `warpscout-account.json` — **имя файла, а не команда**. Его **не надо запускать**, содержимое секретное. `Rotated the keys of the existing WARP account` — сообщение об обновлении ключей, а не об ошибке.

## 3. ГЛАВНЫЙ ШАГ: ищем AWG, где NODE находится НЕ в РФ

**Одна команда для основной задачи:**

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -exclude-country RU -o awg-non-ru-report.txt -conf warp-awg-non-ru.conf
~~~

Именно с этой команды рекомендуется начинать после установки и проверки аккаунта: **не надо перед ней тестировать чистый WG**. Установка WARP-аккаунта общая; AWG использует уже созданный аккаунт.

Что означает каждый параметр:

| Флаг | Зачем |
|---|---|
| `-p awg` | Пробуем **AmneziaWG**, а не обычный WG |
| `-P` | Проверяем реальный туннель, `TUN PING` / `LOSS` и обрывы передачи данных |
| `-jt 4` | Не больше четырёх параллельных туннельных задач |
| `-gen-i1 quic` | Генерируем маскировку первого пакета AWG под QUIC (это **не** MASQUE H3) |
| **`-exclude-country RU`** | **Не допускаем российские Cloudflare NODE/colo в список подходящих кандидатов** |
| `-o ...txt` | Сохраняем подробный отчёт |
| `-conf ...conf` | В **этом же скане** сохраняем конфиг лучшего прошедшего фильтр AWG endpoint'а |

Почему используем `-exclude-country RU` уже **в первом скане**: если фильтр не задать, программа может выбрать ближайший российский узел из-за меньшего ping. Это даст рабочий WARP, но **не выполнит главную задачу**.

**Почему не `-exclude-node DME` по умолчанию?** Это два разных фильтра. `-exclude-country RU` исключает **все российские Cloudflare NODE**, а `-exclude-node DME` — **только конкретный узел DME**. Если на вашем маршруте российский NODE только `DME`, результат может оказаться одинаковым. Но если появится другой российский NODE, вариант с одним `DME` его пропустит. Для цели «colo не в РФ» оставляем **`-exclude-country RU` по умолчанию**; точечный вариант с `DME` есть в разделе 7.

**Не прерывайте скан**, пока не появился итоговый результат. На роутерах с `-P` он может идти существенно дольше простого сканирования. Если команда завершается сообщением, что подходящих endpoint'ов нет, это **не значит, что AWG вообще не работает**: см. раздел 6.

## 4. Выбираем действительно хороший зарубежный colo

В итоговой таблице проверьте **все** эти условия:

1. **NODE / NODE LOCATION:** узел расположен **за пределами РФ**; например, могут встретиться `FRA` (Франкфурт), `AMS` (Амстердам), `ARN` (Стокгольм). Это **примеры, не гарантированный список**.
2. **WORKING / data path:** туннель действительно передаёт данные; вариант с `torn down` не подходит.
3. **LOSS:** желательно **0%** внутри туннеля. Если есть потери, рассматривайте другую строку.
4. **TUN PING:** среди рабочих узлов без потерь выбирайте меньшую задержку. `ENDPOINT PING` вне туннеля недостаточен.
5. **SEEN AS:** смотрите для понимания наблюдаемой выходной географии, но **не смешивайте с NODE**. Даже при NODE `RIX` здесь может быть `RU`.

### Реальная проверка с Keenetic от 18.10.2026: RIX действительно не в РФ

Команда из шага 3 завершилась за 43 секунды и выдала:

~~~text
Proto:       AWG
Nodes:       RIX
Seen as:     RU
Working:     33 / 35 probed
Torn down:   2
Best:        162.159.192.159:2408
TUN PING:    17ms
LOSS:        0%
NODE:        RIX
LOCATION:    Riga, LV
Config:      warp-awg-non-ru.conf
~~~

**Это успешное выполнение задачи «NODE не в РФ»**: `RIX` — Рига, Латвия, а `SEEN AS RU` описывает **выход WARP**, не расположение узла. В живом интерфейсе сканера строка `RU · RIX` также не означает, что Рига находится в России. Ориентируйтесь на конечное поле **`NODE LOCATION`**.

В этом тесте было **33/35 рабочих endpoint'ов**, два оборвались, у выбранного адреса внутри туннеля — **17 мс, 0% потерь**. WARPSCOUT сохранил `warp-awg-non-ru.conf` без дополнительного скана. Это **полевой пример одного uplink в конкретный момент**, а не гарантия сохранения NODE в будущем.

**Главный критерий: сначала non-RU NODE и рабочий туннель без потерь; затем ping и скорость.** Условно «быстрый DME» не лучше «медленного FRA», если ваша цель — именно не российский colo.

WARPSCOUT по умолчанию выбирает лучший вариант **по ping среди оставшихся после фильтра**. Поэтому отчёт нужно проверить: скан с `-P` не даёт автоматической гарантии нулевых потерь или постоянства маршрута. Если для вашей задачи лучше другой обнаруженный colo, переходите к разделу 7.

## 5. Получаем готовый AWG-конфиг

После успешного шага 3 выполните:

~~~sh
ls -lh awg-non-ru-report.txt warp-awg-non-ru.conf
~~~

Увидеть только выбранный адрес (без приватного ключа):

~~~sh
grep -i '^Endpoint[[:space:]]*=' warp-awg-non-ru.conf
~~~

**Итого: найден рабочий AWG endpoint, прошедший фильтр зарубежного NODE, и сохранён его конфиг.** Не надо заново запускать `scan -best`: повторный скан может увидеть уже другой маршрут.

Файл `warp-awg-non-ru.conf` содержит приватные ключи: **не публикуйте и не присылайте его целиком**. Для применения импортируйте его в совместимый AWG-клиент. Если используете [Mihomo Config Builder](https://saymer-alt.github.io/link-generators/), импортируйте в путь **WG/AWG**, **не** во вкладку MASQUE; проверьте поддержку параметров и версии Mihomo, собранный YAML и фактический туннель. WARPSCOUT не применяет конфиг на Keenetic сам.

**После включения VPN перепроверьте реальный NODE/выход в вашем клиенте.** Маршрутизация Cloudflare может измениться со временем, и `-exclude-country RU` действует **в момент сканирования**, а не «прикрепляет» colo навсегда.

Если желаемый зарубежный узел работает, потери приемлемы, а конфиг сохранён — **основная инструкция завершена**.

## 6. Если non-RU NODE не нашлись: выясняем, почему

У этой ситуации **два разных объяснения**. Сначала выполните **диагностический AWG-скан без географического фильтра**:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -o awg-all-nodes-report.txt
~~~

### Ситуация А: AWG работает, но только российские NODE

Если без фильтра появились `WORKING` с `DME` / другими российскими узлами, а с `-exclude-country RU` не было кандидатов, **AWG подключается, но текущий маршрут не удовлетворяет цели**.

Что можно сделать: попробовать поиск в другое время, через **другого провайдера/uplink**, либо увеличенную выборку в следующем скане:

~~~sh
warpscout scan -p awg -P -jt 4 -n 10 -gen-i1 quic -exclude-country RU -o awg-non-ru-expanded.txt -conf warp-awg-non-ru-expanded.conf
~~~

`-n 10` увеличивает число проверяемых адресов на подсеть (обычно 5), **но не гарантирует появление иностранного NODE**. Изменение маскировки I1 само по себе тоже не обещает смену Cloudflare colo. **Не сохраняйте российский NODE под именем «foreign» просто ради успешного отчёта.**

### Ситуация Б: AWG не передаёт данные вообще

Если `WORKING` нет **даже без фильтра**, вероятнее проблема прохождения туннеля/DPI или текущего подключения. Пробуйте варианты I1 по очереди, оставляя фильтр non-RU для финальной цели:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 dns -exclude-country RU -o awg-dns-non-ru.txt -conf warp-awg-dns-non-ru.conf
~~~

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 stun -exclude-country RU -o awg-stun-non-ru.txt -conf warp-awg-stun-non-ru.conf
~~~

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 random -exclude-country RU -o awg-random-non-ru.txt -conf warp-awg-random-non-ru.conf
~~~

Если не помогло, можно дополнительно подобрать junk-параметры:

~~~sh
warpscout find-junk -jt 4 -gen-i1 random
~~~

Используйте найденные параметры только после **полноценного подтверждения `scan -P`**. Успешный `find-junk` — не равен гарантированно рабочему non-RU NODE. Проверьте WAN, DNS, доступность Cloudflare и сетевые политики: настройками AWG невозможно гарантировать доступность внешнего маршрута.

## 7. Выбор конкретных зарубежных узлов и улучшение качества (необязательно)

### Если нужно исключить только DME, а не всю страну RU

Такой фильтр допустим, если вы **точно хотите исключить только DME** и затем **самостоятельно проверите страну каждого найденного NODE**. Он **не гарантирует** non-RU colo, в отличие от географического фильтра шага 3:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -exclude-node DME -o awg-no-dme-report.txt -conf warp-awg-no-dme.conf
~~~

На проверенном маршруте из примера выше `-exclude-country RU` уже сохранил рабочий `RIX (Riga, LV)`, так что **нет необходимости повторять скан только ради замены `RU` на `DME`**. Результаты следующего сканирования могут измениться. **Не заменяйте финальную проверку `NODE LOCATION` названием файла `no-dme`.**

### Если хотите выбрать конкретный зарубежный NODE

Если скан показал несколько зарубежных NODE и **вы хотите выбирать осознанно**, укажите только интересующие вас коды. Например, **только если `FRA` и `AMS` реально появились в вашем отчёте**:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -node FRA,AMS -exclude-country RU -o awg-fra-ams-report.txt -conf warp-awg-fra-ams.conf
~~~

Так программа выберет лучший endpoint **среди двух заданных узлов**. Можно искать конкретную страну узла (например, Германию и Нидерланды):

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -country DE,NL -o awg-de-nl-report.txt -conf warp-awg-de-nl.conf
~~~

Если какой-то иностранный узел нежелателен лично вам, например `ARN`, **не делайте этот запрет универсальным**. Это отдельный фильтр под конкретную задачу:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -exclude-country RU -exclude-node ARN -o awg-non-ru-no-arn.txt -conf warp-awg-non-ru-no-arn.conf
~~~

**Когда важнее скорость, чем ping**, добавьте измерение скачивания и выбор по скорости. Это медленнее и может увеличить трафик:

~~~sh
warpscout scan -p awg -P -jt 4 -gen-i1 quic -exclude-country RU -speed -best-by speed -o awg-non-ru-speed.txt -conf warp-awg-non-ru-speed.conf
~~~

Во всех вариантах сначала проверьте фактический `NODE`, рабочий data path и `LOSS`, а только потом доверяйте `warp-*.conf`. Пустая таблица означает, что под выбранными фильтрами подходящих endpoint'ов не нашлось, но не доказывает полной блокировки WARP.

## 8. Почему здесь вообще нет команд обычного WG

В реальном тесте на Keenetic (18.10.2026) WARPSCOUT использовал существующий аккаунт и сообщил:

~~~text
Phase 1: probing reachable WARP ports: reachable ports [2408 500 1701 4500]
Phase 2: verifying tunnels (proto=wg): done in 2m26s
no working endpoints found - try -p awg -gen-i1 quic
~~~

**Что это означает:** UDP-порты ответили на начальную проверку, но **ни один полноценный обычный WG-туннель не прошёл проверку передачи данных**. То есть `reachable ports` — **не** `working tunnel`. Мы не заставляем новичка повторять эти 2 минуты 26 секунд ради ожидаемого отказа.

**Действие после такого сообщения:** вернитесь к **шагу 3**, запустите AWG с `-gen-i1 quic` и фильтром `-exclude-country RU`. Не требуется переустановка или новая регистрация.

Это подтверждение для **проверенного подключения**, а не утверждение, что обычный WG блокируется у абсолютно всех провайдеров. В **пошаговой инструкции для фильтрованных сетей WG больше не сканируем вообще**.

## 9. MASQUE H2 / H3 — только дополнительные эксперименты

**Не используйте MASQUE как замену задаче поиска конкретного зарубежного colo через AWG.** В проверяемой версии WARPSCOUT для MASQUE **не поддерживаются фильтры NODE/COUNTRY**: путь выбирает сама сеть/Cloudflare. Даже рабочий MASQUE с ближайшим `DME` не гарантирует зарубежного узла, а вручную указать `-exclude-country RU` для H2/H3 нельзя.

Ещё одна особенность: MASQUE **зависит от провайдера**. В наших дачных испытаниях 2026-09-25:

| Подключение | AWG | MASQUE H2 / TCP | MASQUE H3 / QUIC |
|---|---|---|---|
| GSM/LTE (MCN/T2) | Работал; видели non-RU NODE | Работал с найденным SNI | `find-sni` находил кандидатов, но полноценный data path не проходил |
| Проводной Mynetcity | Работал; видели non-RU NODE | Работал с найденным SNI | Проходил полноценную передачу данных |

Это **исторические наблюдения**, не обещание для любого провайдера или сегодняшнего маршрута.

**Если хотите просто посмотреть, работает ли MASQUE на вашем WAN:**

H2 — сначала:

~~~sh
warpscout find-sni -p masque-h2 -jt 4
~~~

Затем **замените пример SNI** `www.apple.com` на кандидат, найденный на своём роутере:

~~~sh
warpscout scan -p masque-h2 -P -jt 4 -masque-sni www.apple.com -o masque-h2-report.txt -conf warp-masque-h2.yaml -conf-type mihomo
~~~

H3 — сначала:

~~~sh
warpscout find-sni -p masque -jt 4
~~~

Затем **замените пример SNI** `cdn.jsdelivr.net` на найденный:

~~~sh
warpscout scan -p masque -P -jt 4 -masque-sni cdn.jsdelivr.net -o masque-h3-report.txt -conf warp-masque-h3.yaml -conf-type mihomo
~~~

**Успешный `find-sni` не доказывает, что MASQUE передаёт данные.** Если финальный `scan -P` не прошёл, считайте транспорт неработающим на текущем маршруте, несмотря на предварительные цифры. Менять `NODE` в MASQUE так же, как в AWG, этим инструментом нельзя.

Для WARPSCOUT/Mihomo `type: masque` YAML генератор link-generators импортирует identity, SNI и точный `server:port` (в отличие от legacy identity-only), но импорт endpoint'а не создаёт новый путь Cloudflare/colo. **MASQUE не обязателен для выполнения основной цели этого руководства.**

## 10. Частые проблемы

| Видите в терминале | Что означает / что сделать |
|---|---|
| `Unknown package 'warpscout'` | Штатный fallback на GitHub IPK, если в конце установка успешна |
| `API unreachable directly` | Подождите окончания регистрации; проверьте файл аккаунта |
| `-sh: warpscout-account.json: not found` | Это файл, не команда. Проверка: `ls -lh /opt/etc/warpscout/warpscout-account.json` |
| `invalid value "" for flag -jt` | Пустая переменная. Здесь **везде `-jt 4`** |
| `no working endpoints found - try -p awg -gen-i1 quic` после обычного WG | WG-туннель не прошёл проверку; **сразу переходите к AWG из шага 3, WG не повторять** |
| `No working endpoints found` с `-exclude-country RU` при AWG | Сначала диагностический AWG-скан **без фильтра** из раздела 6 |
| Результат только `DME` | Рабочий AWG ≠ non-RU NODE; попробуйте другой WAN/время, см. раздел 6 |
| Зарубежный NODE, но `SEEN AS RU` (например, `RU · RIX`) | **RIX находится в Риге, LV**, несмотря на `SEEN AS RU`. Проверяйте столбец `NODE LOCATION`; выходной GeoIP может остаться RU |
| Нужно исключить именно DME | Используйте `-exclude-node DME` из раздела 7, **но он не исключает все российские узлы** |
| Есть `WORKING`, но `LOSS` не 0% | Рассмотрите другой endpoint/NODE, не судите только по `ENDPOINT PING` |
| Не появился `.conf` | Сначала проверьте, есть ли хоть один подходящий endpoint **после фильтра** |
| MASQUE H2/H3 не заработал | Это факультатив, не мешает использованию AWG |

## Что нужно помнить

- **Результат «успех»:** AWG с реальной передачей данных, `NODE LOCATION` не РФ, приемлемыми потерями/задержкой, сохранённым `.conf`. Предварительный WG-тест не нужен.
- **Результат «частичный»:** AWG работает, но только `DME` / другой российский узел. **Не выдаём за иностранный colo.**
- **Результат «не подтверждён»:** endpoint отвечает на ping или `find-sni` показывает успех, но полноценный тест данных не пройден.
- **После импорта:** проверьте фактический маршрут и сервис. Коды узлов, RTT, SNI и работающие IP **могут меняться со временем**. Не считайте выбор non-RU NODE пожизненной фиксацией.

Для дальнейших сравнений достаточно сохранить обезличенные данные: модель Keenetic, провайдера/uplink, дату, `NODE`, `SEEN AS`, `TUN PING / LOSS`, количество рабочих, endpoint `IP:port`. **Не публикуйте** `warpscout-account.json`, ключи и содержимое `warp-*.conf`.
