# Owner Experience Gate v1.0 — link-generators

Единый стандарт пользовательской приёмки для проектов `saymer-alt`.
Для генератора он **использует существующие тесты**, не создаёт ещё один
браузерный фреймворк и не меняет код, данные или YAML продукта.

## Цель

Зелёный CI подтверждает проверяемые свойства конкретного SHA, но не
гарантирует, что новый пользователь интуитивно понимает весь интерфейс.
Кнопка может технически работать, а результат — оказаться за пределами
видимой области. Поэтому каждой найденной владельцем UX-проблеме
соответствует воспроизводимый browser regression с проверкой наблюдаемого
результата (видимость, позиция в viewport, фокус, сообщение, состояние).

## Обязательный автоматический Gate

1. `tests/fixtures/owner-experience-regressions.json` — реестр **реальных
   находок** владельца: симптом и точные префиксы именованных Playwright
   сценариев. Исторические UX-01…08 не удалять ради зелёного статуса.
2. `python3 tools/owner-experience-gate.py` — проверяет, что каждый
   зарегистрированный сценарий существует и соответствующие jobs
   (`tests/owner-ux-browser.cjs`, Firefox/WebKit, release journey)
   остались подключены в `Generator CI`. Сам он **не запускает браузер**
   и не претендует на функциональный PASS.
3. `tests/owner-ux-browser.cjs` действительно запускается в Chromium,
   Firefox и WebKit; проверки выполняют реальные click/keyboard/pointer
   действия, отслеживают DOM, viewport, focus и сообщения.
4. `tests/final-release-browser.cjs` проверяет многосекционный путь и
   ширины экрана; параллельно действуют существующие unit, fieldtest,
   chaos, DNS и real-Mihomo parse/runtime gates.
5. При новом UX-дефекте: сначала воспроизведение **FAIL на исходном
   SHA**, затем минимальное исправление и **PASS** на исправленном;
   добавление нового `UX-09` (и далее) с тестом и записью в реестре
   производится одним PR. Гипотезы, неподтверждённые подозрения и
   трудновоспроизводимые наблюдения не объявлять «FIXED».

При удалении теста, изменении имени сценария или отключении матрицы
Gate должен упасть. Существующий guard Generator CI отдельно проверяет,
что новые `tests/*.cjs` зарегистрированы в workflow. Все результаты
относятся только к точному commit SHA.

## Короткая Owner Acceptance перед stable

Владелец проверяет конкретный preview artifact **того же SHA**, который
будет предложен к promotion. Регулярный набор (~5–10 минут):

- Создать несколько DPR-политик AI подряд: появление карточки рядом с
  кнопкой, фокус, уникальность имени, порядок; импорт MagiTrickle рядом.
- Builder и Config Studio: Fit/100%/+/−/pan/focus на небольшом и
  крупном графе, обычное колесо прокручивает страницу; YAML неизменен.
- Mihomo Controller: пустой URL и скопированная ссылка `/ui/#/overview`
  приводят к корректному API base; без реального контроллера отмечать
  `NOT RUN`, а не `PASS`. CORS/PNA нельзя обойти через worker.
- Routing Inspector с пустым полем до первой сборки: очевидный
  Build-and-check, явное согласие до сетевого получения URL-подписок;
  Domain Coverage не показывает устаревший snapshot.
- Project Save/Load, Reverse Preview/Cancel/Undo: отмена не меняет
  проект; повторно проверить ранее наблюдавшийся необъяснённый
  timeout кнопки Cancel. Не объявлять его корневую причину найденной.
- Основной Build, `mihomo -t` с собственной *резервной копией* YAML,
  один локальный сценарий там, где реально доступен подходящий стенд.
  Реальный WG/WAN handshake, отсутствие DNS leaks и поведение Keenetic
  остаются отдельными доказательствами, не экстраполируются из CI.

Фиксировать на каждый релиз: timestamp, SHA, версию браузера,
проверенные сценарии и их `PASS/FAIL/UNKNOWN/NOT RUN`, CI + preview URLs,
скриншоты без секретов, неустранённые ограничения, решение владельца.

## Что разрешено автоматически, а что нет

- CI: синтетические fixtures, изолированный Playwright, mock APIs,
  локальные loopback labs без изменения системной сети.
- Только с отдельным разрешением: доступ к настоящему Mihomo
  Controller, URL-подпискам, VPS/Keenetic, реальным ключам, DNS/TUN,
  маршрутам, WAN и изменениям production.
- Автоматический агент может подготовить release-candidate отчёт,
  но не выдаёт `Owner GO` за человека и не продвигает `main → stable`
  без явного согласия. Релиз и теги — отдельное решение.

Зелёный автоматический Gate означает **CI user-scenario evidence**, а не
полную human usability или runtime/field proof. Это применяет тот же
Owner Experience Gate v1.0, что используется KAS, AMG и VPS Gateway,
с учётом специфики браузерного продукта.
