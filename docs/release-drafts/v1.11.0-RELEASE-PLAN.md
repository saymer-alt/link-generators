## Анализ истории и merge simulation

Stable имеет 25 коммитов вне main; main — 225 вне stable. Stable включает прежние production promotions, SEO-backport #241 и GSC verification #243. Нужен обычный merge с сохранением двух историй, без force-push/reset/замены stable целым main.

Первичная локальная симуляция `stable + main` дала пять конфликтующих файлов:

| Файл | Разрешение production-кандидата |
|---|---|
| CHANGELOG.md | Актуальная сводка v1.11 + неизменная история выпущенных версий; Unreleased переводится в `[1.11.0]` только в кандидате |
| docs/GENERATOR-GUIDE.md | Сохранить main-инструкцию, в кандидате указать production 1.11.0; main dev не менять |
| index.html | Сохранить SEO и функциональный main-код; изменить только GENERATOR_META кандидата на 1.11.0/stable |
| quick-start.html | Сохранить SEO и новые разделы main; убрать устаревшие dev/main подписи только в кандидате |
| tests/version-badge.cjs | Сохранить новые проверки main, pin версии/канала заменить на 1.11.0/stable для кандидата |

Конфликты SEO в HTML — пустая строка, не разница значений metadata. Sitemap и Google verification совпадают в main/stable. SECURITY.md из main добавляется в production; runtime переносится без ручной правки и проверяется против canonical source. Functional index-код после разрешения должен совпадать с main, кроме GENERATOR_META; новая функциональность в promotion не добавляется.

Для окончательной симуляции использовать docs-кандидат этого PR поверх зафиксированного main. До promotion документационный PR должен пройти CI и попасть в main по отдельному разрешению. Если main/stable/source изменятся, симуляция и проверки повторяются на новых refs.

## Точная безопасная последовательность

1. Получить решение владельца по документационному PR в main; после merge проверить новый exact main SHA и полный main CI. Версия main остаётся dev.
2. Повторно прочитать refs. Согласовать production-кандидат, содержащий актуальный main, прежнюю stable-историю и только отдельные release metadata изменения. Получить **Owner Stable Promotion GO** на конкретный diff/tree и exact head.
3. Открыть/обновить обычный promotion PR в stable. При изменении refs повторить merge simulation и полный CI; не использовать force-push и не терять SEO/GSC/security изменения.
4. После разрешённого merge зафиксировать фактический `git rev-parse origin/stable`, проверить полный CI именно этого SHA и Pages deploy именно этого commit. Протестировать публичную страницу: 1.11.0/STABLE, синтетическая Build, Quick Start, sitemap и Google verification. При неготовом Pages/CI остановиться.
5. Получить отдельный Owner Tag/Release GO. Только затем создать tag v1.11.0 на проверенном production SHA, убедиться, что peeled tag == принятый stable SHA, заполнить provenance в body и опубликовать Release. Не использовать main как target релиза.
6. Проверить tag/Release/Pages после публикации. Без нового Owner GO ни один production ref, тег или Release не изменяется.

SHA итогового production merge заранее не обещается: GitHub создаст новый merge commit. Кандидат фиксирует tested tree; production SHA получают после разрешённого merge и проверяют отдельно. При том же дереве, но новом commit SHA, требуется проверка CI/deploy нового SHA.
