# Короткая инструкция по генератору

Короткая человеческая инструкция: как за пару минут получить рабочий конфиг.
Совсем короткая версия с картинкой-сценариями — [quick-start.html](../quick-start.html).
Технические подробности — по ссылкам в конце.

> В шапке страницы справа от заголовка — бейдж версии (в production — `v1.10.0 · STABLE`; на main в разработке — `v1.11.0-dev · MAIN`):
> видно, какую сборку вы открыли. `MAIN`/`STABLE` — метка канала сборки
> (development/production), а не определение ветки; при release promotion
> владелец переводит её на стабильную. Технические детали — [DEVELOPMENT.md](DEVELOPMENT.md).

## 1. Сначала выберите, где будет работать Mihomo

Во вкладке Builder пять рабочих областей. Начните с **🏠 Быстрого старта**: платформа → ссылки/URL-подписки или WG/AWG → основные настройки → **⚡ Build Config** → **Скачать YAML**. Скачать/скопировать можно только после базовой проверки; она не заменяет `mihomo -t`.

**🌐 Маршрутизация и DNS** содержит фильтры подписок, устройство/HWID, импорт runtime-узлов, DPR/MagiTrickle, эшелоны и WG DNS/dialer. **🔍 Диагностика** объясняет последний Build и доступна независимо от DPR. **🧪 Лаборатория** — экспериментальная физическая модель, What-if и наблюдения контроллеров; она не выполняет обычный Build и не обещает physical failover. **⚙️ Дополнительно** — дашборд, health-check, Modern REALITY и расширенные входы/TUN.

Навигация вверху прокручивает к разделу и переводит фокус; «Все инструменты — экспертный доступ» открывает нужную существующую панель. Переходы ничего не включают, не строят YAML и не отправляют запросы. WARP и Config Studio остаются отдельными вкладками. В первой версии нет глобального переключателя, скрывающего активные настройки: простой путь — Quick Start, полный доступ — остальные области и каталог. Данные и все предупреждения сохраняются.

Первый вопрос наверху вкладки Builder: **«🎯 Где будет работать Mihomo?»**

### 🏠 Роутер / обычный TUN (Keenetic) — по умолчанию

Mihomo работает на домашнем роутере и поднимает TUN-интерфейс: весь трафик
устройства идёт через него. Профиль включает TUN, MIPS stack, Mixed Port 7890
и Allow LAN — все параметры потом можно менять вручную.

### 🖥️ VPS — локальный Mihomo / SOCKS для Xray / 3X-UI

На VPS уже работает Xray/3X-UI (или другое приложение), которое отправляет
трафик в Mihomo через `127.0.0.1:7890`. Профиль выключает TUN, MIPS и Allow LAN
(внешний доступ к 7890 не нужен) и оставляет только локальный SOCKS-вход.
Схема: `Xray/3X-UI → 127.0.0.1:7890 → Mihomo → proxy`.

### 🌐 VPS Transparent Gateway (amnezia-mihomo-gateway)

Специальный сценарий: transparent-gateway с Linux policy routing / iptables /
Docker / AmneziaWG. Генератор создаёт **только Mihomo-часть** (TUN `tun-mihomo`,
DNS-перехват fake-ip, `auto-route: false`); Linux routing и firewall настраивает
[amnezia-mihomo-gateway](https://github.com/saymer-alt/amnezia-mihomo-gateway).
Allow LAN в этом профиле выключен принудительно (router-only опция) — gateway
принимает трафик через TUN + policy routing, а не через LAN-listener.
Для обычного VPS с Xray/3X-UI используйте предыдущий профиль.

#### 🌐 Удалённый доступ к Web UI нескольких VPS (SSH local forwarding)

Controller/Web UI Mihomo в обоих VPS-профилях всегда слушает только
`127.0.0.1:9090` — это фиксированный safety-контракт, порт на VPS не меняется.
Конфликт нескольких одновременно открытых VPS решается на компьютере — разными
локальными SSH/PuTTY forwarded-портами:

```text
VPS-SE: local 9091 → remote 127.0.0.1:9090
VPS-EE: local 9092 → remote 127.0.0.1:9090
VPS-RU: local 9093 → remote 127.0.0.1:9090
```

Два разных понятия, которые не стоит путать:

- **remote port на VPS** — порт, на котором Mihomo слушает на самом сервере
  (`127.0.0.1:9090` на всех VPS, одинаково);
- **локальный forwarded-порт** — порт на вашем компьютере, через который туннель
  (`ssh -L 9091:127.0.0.1:9090`, PuTTY «Local port») выпускает на Web UI
  (`http://127.0.0.1:9091/ui/`).

## 2. Входные данные

В поле «Основные прокси-ссылки / URL-подписки» вставьте:

- обычные прокси-ссылки: `vless://`, `trojan://`, `ss://`, `masque://`… — напрямую;
- ссылки на подписки (HTTP(S) URL) — при включённом режиме «URL-подписки»;
- можно смешивать: подписка + обычные ссылки.

WARP-конфиги: вкладка **⚡ WARP MASQUE Links** генерирует `masque://` ссылки —
кнопка «🚀 В Mihomo Builder» переносит их сюда. WireGuard/AmneziaWG — кнопка
«📂 Загрузить .conf / .wg / .awg»: каждый файл станет отдельным WireGuard-прокси.
Повторное нажатие **добавляет** файлы к уже загруженным (не заменяет!);
загруженное видно списком с удалением по одному и кнопкой «🧹 Очистить все».

### ⚡ WARP-вкладка: импорт WARPSCOUT / Mihomo MASQUE

Кроме классического WARP YAML (бот) вкладка понимает YAML с прокси
`type: masque` (например, вывод WARPSCOUT или готовый Mihomo-конфиг).
«🔍 Распарсить» сканирует **все** прокси, а не только первый:

- `network: h2` → транспорт **H2 / TCP**; без него (или пустой) → **H3 / QUIC**;
  любое другое значение (`tcp`, `h3`, `foo`…) — UNSUPPORTED кандидат: он
  показывается в плашке с именем и сырым токеном и **не** импортируется
  (H3 без source-proof не предполагается);
- общая identity (ключи, ip, ipv6, dns) берётся из **фактически выбранной пары**
  транспортов: H3 и H2 с разными ключами/IP — разные WARP-аккаунты, такая пара
  отвергается явно (какие профили конфликтуют — названо; значения секретов —
  никогда); гибрид «identity A + endpoint B» не создаётся;
- найденный endpoint и SNI каждого транспорта попадают в секцию
  «⚙️ Advanced MASQUE» как **точные** значения и используются дословно —
  с объяснением в плашке «🛰 WARPSCOUT / Mihomo MASQUE detected»;
- пустой SNI в кандидате — сознательный fallback на общий SNI из формы
  (плашка это явно называет); SNI не выдумывается;
- транспорт без кандидата остаётся на встроенной стратегии генератора;
- несколько кандидатов одного транспорта — явный выбор по имени (никакого
  молчаливого «первого»); пока выбор не сделан, ничего не применяется, а
  несовместимая пара после выбора отвергается с открытым селектором.

Приоритет на каждый транспорт: **точный endpoint → свой список портов →
встроенная стратегия**. Точный endpoint не переписывается анти-корреляцией
(она управляет только сгенерированными endpoint'ами). Свой список портов
полностью заменяет встроенный выбор. Порты — целые 1..65535 («443abc» —
ошибка, а не 443). Endpoint — `IPv4:port` или `hostname:port`; IPv6
отвергается явно (контракт MASQUE/IPv6 не доказан). Помните: endpoint,
порт и SNI из скана — **наблюдения**, а не вечные свойства: colo/доступность
меняются, при проблемах сначала перосканируйте. Ключи живут только в памяти
страницы — ни localStorage, ни sessionStorage, ни URL.

## 3. Основные переключатели

| Переключатель | Что делает |
|---|---|
| 🛡️ TUN Interface | Системный TUN: весь трафик устройства через Mihomo. Нужен на роутере; на VPS с локальным Xray — выключен. |
| ⚡ MIPS stack | Стек обработки TUN-трафика (не процессор!). По умолчанию MIPS; требует Mihomo ≥ 1.19.31, иначе gVisor. |
| 🔌 Mixed Port 7890 | Локальный HTTP+SOCKS вход Mihomo. |
| 🌐 Allow LAN | Доступ к Mihomo из локальной сети (добавляет `bind-address: "*"`). Доступно только в профиле «Роутер / обычный TUN»; в обоих VPS-профилях выключено принудительно. |
| 🖥️ Web UI | Веб-дашборд управления (MetaCubeXD) на порту 9090. |
| ⚙ Расширенный TUN stack | `system`/`mixed` — экспериментальные (внутри ADVANCED-секции); обычно достаточно MIPS/gVisor. |

## 4. Подписки

Режим «📡 Использовать URL-подписки» превращает HTTP(S) ссылки в `proxy-providers`:
Mihomo сам скачивает и обновляет списки узлов (раз в 12 часов + health-check).

- **🚫 Exclude Filter** — regexp по именам узлов подписки: совпавшие узлы
  исключаются. Важно: regexp сравнивается с **фактическим именем** узла.
  Латинский `ru|russia` не совпадёт с кириллическим «Россия» — для таких
  подписок пишите кириллический вариант (`Россия|Москва`). Семантика
  provider-level vs group-level: [MIHOMO.md](MIHOMO.md).
- **📱 Device Model** — необязательное понятное имя устройства (например:
  `Keenetic Giga KN-1012`, `Windows-PC`), которое панель подписки увидит как
  заголовок `x-device-model` в запросах списка серверов. Если пусто, в таких
  запросах используется служебное `Saymer Link Generators Preview`; на
  стабильный HWID значение не влияет.
- **📋 Показать серверы подписки** — opt-in toggle в блоке основных переключателей (по умолчанию
  выключен): при выключенном переключателе подписка браузером не запрашивается
  вовсе, provider-YAML собирается без обращения к сети. После включения список
  имён узлов запрашивается только по явной кнопке «Получить список»: поиск,
  «выбрать все»/«снять все», счётчики; отмеченные галочками узлы становятся
  точными исключениями и объединяются (OR) с ручным Exclude Filter. Запросы
  используют стабильный идентификатор генератора (HWID) — новое устройство не
  регистрируется на каждый Build. При CORS-проблемах используется проектный
  fallback-воркер (URL подписки при этом виден его инфраструктуре).
- Некоторые панели (например, Geodema/Remnawave) требуют заголовок **`x-hwid`** —
  генератор добавляет его автоматически; без него панель может вернуть
  заглушку «App not supported» вместо списка узлов.

## 5. Политики по доменам (DPR)

Режим «🚦 Политики по доменам»: вы создаёте категории («AI», «YouTube»…)
с списком доменов, и трафик на эти домены идёт через отдельную группу выхода.
Остальной трафик идёт как раньше — завершающее правило `MATCH,GLOBAL` не меняется.

- «➕ Добавить политику» → выберите шаблон (AI / YouTube / Telegram / Google /
  Direct / Proxy) или впишите свои домены, по одному в строке. Голый домен = домен
  со всеми поддоменами; поддерживаются также `DOMAIN-SUFFIX,…`, CIDR, GEOSITE.
- Правила указывают на группы, группы — на подписку: состав подписки меняется,
  правила пересобирать не нужно.
- Нераспознанные строки пропускаются с предупреждением (конфиг всё равно собирается).
- С «на каждый прокси» режим несовместим (выбранное не применяется).
- Требуется Mihomo ≥ 1.19.27. Для pure-IP-клиентов (без доменов в запросе)
  на роутере домен «увидеть» сложнее — в профиле vps-gateway для этого есть
  автоматический пакет домен-детекта.

Подробно: [POLICY-ROUTING.md](POLICY-ROUTING.md).


#### Шаблон «🚀 Proxy (свои домены через прокси)»

Симметрия к «⬇️ Direct»: создаёт политику с таргетом **GLOBAL** — «лучший доступный
прокси». Важно: GLOBAL — строгий «через прокси» в том смысле, что группа GLOBAL
не содержит DIRECT ни в одном режиме (static — листья+REJECT; подписки — листья+
use-подписки+REJECT; AW — PRIMARY/FALLBACK), и вручную переключить её на DIRECT
нельзя. Но конкретный прокси внутри GLOBAL выбирается (Fastest/вручную в дашборде)
— если нужен строго фиксированный прокси, выберите его leaf в таргете карточки
(селект содержит только реально существующие цели). Домены впишите свои.


### WG/AWG: IPv4-only режим

Импортированные WG/AWG-профили нормализуются в IPv4-only режим: IPv6-поля
(Address/AllowedIPs/DNS) из импортированного профиля не попадают в итоговый Mihomo YAML,
endpoint-транспорт закреплён за IPv4 (`ip-version: ipv4`). IPv6-only профили и профили
с IPv6 literal endpoint отклоняются с понятной ошибкой. MTU при этом не меняется.

### WG/AWG: стабильность AWG (#137)

Два явных переключателя в разделе WG/AWG:

- **«🛡 Поддерживать AWG-соединение через NAT (keepalive 25 с)»** — включён по умолчанию.
  Если в профиле нет совместимого целого `PersistentKeepalive`, при сборке Mihomo получит
  `persistent-keepalive: 25`; диапазон вроде `25-35` сводится к 25 с явной диагностикой
  (фиксированный 25 **не эквивалентен** исходной random-range семантике). Существующее
  целое значение (включая 0 = disabled) не меняется. Действует только на AWG-профили,
  plain WireGuard не затрагивается. Выключение возвращает строгий контракт: диапазон
  не эмитится, WARN остаётся.
- **«🧪 Тест обрывов: отключить RandomTrailers»** — по умолчанию выключен. Диагностический
  override: у AWG-профилей с включённым RandomTrailers при сборке он отключается
  (`on → off`) с красным предупреждением. Это controlled experiment для локализации
  обрывов, а **не** доказанный универсальный fix; MTU, ключи и остальные поля не меняются.

Любое применение обоих переключателей видно в diagnostic report профиля и на его карточке
(«что сделает сборка»); оригинальные профили не мутируются.

### Routing Inspector / Diagnostics

Внутри панели политик — сворачиваемый блок «DIAGNOSTICS — Routing Inspector / Diagnostics».
Он работает по **итоговому сгенерированному YAML** (после Build) и только офлайн:

- **Routing order** — человекочитаемый порядок правил с семантическим путём:
  `1. AI → SELECT-группа «AI» → [AI-AUTO / ⚡ Fastest / GLOBAL / DIRECT]`, `… Всё остальное → GLOBAL`;
  тип группы и участники берутся из итогового конфига (не хардкод); под списком — честная
  приписка «Фактически выбранный участник определяется Mihomo во время работы»
  (для `select`/`url-test`/`fallback` конечный runtime-member статически не определим);
- **Проверка домена/IP** — поле «Проверить домен или IP»: инспектор показывает победившее правило
  (номер + RAW), маршрут (тот же семантический рендеринг), альтернативные совпадения ниже по списку
  и объяснение «Mihomo применяет первое подходящее правило»;
- **Свежесть (stale build)** — диагностика анализирует результат **последнего Build**. Если после
  сборки изменить любой input, влияющий на конфиг, над блоком появится заметное
  «⚠ Настройки изменены после последнего Build…» — вывод остаётся видимым (для сравнения),
  но помечен как предыдущая сборка; скрытый пересбор не выполняется никогда. Чисто визуальные
  действия (например, ввод в поле проверки домена) ложную метку не дают;
- **Domain Coverage Checker** — вложенный подраздел DIAGNOSTICS: вводите домены (по одному
  в строке) — для каждого показывается победившее правило (первое совпадение), inline-правило
  или провайдер, и статический путь до цели насколько это доказуемо
  (`→ GLOBAL → [⚡ Fastest / A / wg-simple-a (через wg-simple-b) / REJECT] — runtime-selected`).
  «Совпадает с правилом» ≠ «гарантированно идёт через конкретный прокси»: для
  select/url-test/fallback участник определяется Mihomo во время работы (помечается
  `runtime-selected`). GEOSITE/GEOIP/внешние провайдеры — честный UNKNOWN; непокрытый домен —
  UNCOVERED/FALLBACK; мусорный ввод — INVALID. Snapshot последнего Build (stale помечается).
- **Предупреждения** — точные дубликаты правил и записей inline-провайдеров,
  перекрытые правила (DOMAIN-SUFFIX раньше уже покрывающего DOMAIN/более узкого SUFFIX),
  недостижимые правила после MATCH, неиспользуемые провайдеры, один домен в разных политиках
  (информация — порядок решает);
- **Rule Provider Explorer** — вложенный сворачиваемый подраздел DIAGNOSTICS: read-only
  инвентарь всех `rule-providers` итогового конфига в порядке YAML. Сводка: провайдеры /
  используются / не используются / inline / внешние (только доказуемые http и file) /
  other-unknown (строка появляется, только если есть типы, отличные от inline/http/file) /
  отсутствующие ссылки. Карточка каждого
  провайдера: `type`, `behavior`, `format`, `source` и простые метаданные (`url`, `path`,
  `interval`, `proxy`, …), плюс все ссылки «used by: rule #N → TARGET». Провайдер без ссылок
  помечается «UNUSED», ссылка на несуществующий провайдер — «Referenced but missing» (проблема
  показывается, но не «чинится» автоматически). Для inline-провайдеров — число записей payload,
  локальный размер текста и поиск по подстроке (case-insensitive, только по уже доступному
  payload, без сохранения; показ ограничен первыми 500 записями с явной пометкой, счёт — по
  полному payload). Содержимое внешних (http/file) провайдеров браузером **не загружается**
  (никаких fetch/HEAD), MRS не декодируется — показываются только метаданные и
  «unavailable offline». Explorer ничего не меняет в YAML и ничего не сохраняет.

**Честные ограничения**: точно анализируются DOMAIN, DOMAIN-SUFFIX, DOMAIN-KEYWORD, MATCH и
inline-провайдеры политик; DOMAIN-REGEX/DOMAIN-WILDCARD, GEOSITE/GEOIP, внешние (http/file)
провайдеры и DNS-зависимые IP-правила возвращают **UNKNOWN** с причиной. Инспектор не
заменяет диагностику самого Mihomo и ничего не меняет в конфиге; запросы никуда не
отправляются и не сохраняются.

## 6. Автоматический режим белых списков (БС)

Включите «Автоматический режим белых списков» → появится второе поле. Верхнее
поле — основные серверы, второе — резерв (то, что работает при блокировках).
При недоступности основных выходов Mihomo сам переключится на резерв и вернётся
обратно по плановой проверке. Переключение не мгновенное; «DIRECT» в цели не
добавляется (если мертвы оба набора — трафика не будет). Опции «на каждый
прокси» в этом режиме отключаются, а профиль развёртывания временно работает
в router-совместимом варианте (ваш выбор профиля сохраняется и возвращается).

Подробно: [AUTO-WHITELIST.md](AUTO-WHITELIST.md).

## 7. WARP/WireGuard через dialer-proxy

У каждого загруженного WG/AWG-профиля в карточке есть выбор **«Подключение»**:

- **Напрямую** (по умолчанию) — обычный WireGuard-выход;
- **Через промежуточный proxy** — туннель пойдёт через указанный proxy или
  группу («туннель в туннеле»): WARP подключается к Cloudflare из сети другого
  узла/страны. Имя таргета вводится тут же, у конкретного профиля; у другого
  профиля может быть свой таргет (или «Напрямую»).

Поля «Имя dialer-группы» / «Транзитные узлы» / «URL-подписки для dialer-группы»
описывают состав группы; использует её или нет — решает каждая карточка
отдельно. Новый профиль наследует заполненное глобальное поле как таргет по
умолчанию (миграция старого сценария).

Два полевых факта:

1. **Промежуточный узел должен реально поддерживать UDP relay.** Рабочие
   сайты/TCP через узел сами по себе не означают, что через него поднимется
   WireGuard/WARP. Проверяется только фактическим тестом.
2. **Переключение узла в dialer-группе — не мгновенная смена пути.** Уже
   установленный WireGuard-хендшейк может держать старый transport path дольше
   150 секунд. Для гарантированной смены пути нужен пересоздание outbound
   (reload конфига/перезапуск Mihomo). Смена colo Cloudflare — наблюдение,
   не гарантия: Cloudflare выбирает ingress сам.

## 8. ADVANCED Per-Proxy

Секция «ADVANCED — Отдельный вход на каждый прокси» по умолчанию свёрнута.
Внутри: режим, создающий отдельный TUN/SOCKS-вход **для каждого** прокси.
Для обычного использования не нужен. Раскрытие секции ничего не включает —
включается только явный master-переключатель.

## 8.1 Physical Topology

Панель «🌐 Physical Topology» описывает **физическую** цепочку из независимых
узлов (#149): Client → ENTRY → TRANSIT(0..N) → EXIT [→ FINAL OVERLAY] →
Internet. «Загрузить демо-топологию» подставляет синтетический пример
(Moscow → Estonia → Sweden → WARP, без реальных адресов); «Проанализировать»
проверяет линейную цепочку, а what-if показывает CHAIN_UNAVAILABLE при отказе
узла. Runtime Evidence по явному действию читает `/version` и `/proxies` на
указанных контроллерах и сравнивает наблюдаемое состояние с заданной моделью.
Это не проверка доступности физического узла и не доказательство packet path.

«Подготовить артефакты узлов» создаёт `config.yaml` только для поддержанных
контрактов SS/SOCKS/HTTP; остальные транспорты получают `contract.md`.
PLACEHOLDERS_REQUIRED и EXTERNAL_CONTRACT_REQUIRED не являются готовыми к запуску
конфигами. READY проверяется Mihomo в CI на поддерживаемых версиях. Physical
Topology использует отдельную модель и не меняет обычный Mihomo Build
автоматически. Данные панели остаются в памяти вкладки. Подробности: [архитектура](research/PHYSICAL-MULTIHOP-ARCHITECTURE.md), [генерация](research/PT-GENERATION.md), [Runtime Evidence](research/PT-RUNTIME-EVIDENCE.md).

## 8.2 Config Studio — анализ и правка готового конфига (#176/#178)

Вкладка «🔎 Config Studio» принимает уже работающий Mihomo-конфиг (вставка или
файл `.yaml`/`.yml`) и локально показывает сводку, граф зависимостей,
маршрутизацию (покрытие доменов / проверка одного домена), semantic trace и
диагностики (висячие ссылки, дубликаты, неиспользуемые объекты, циклы групп).
Значения секретных полей скрываются и в выводы не попадают; конфиг никуда не
отправляется и не сохраняется.

Панель «✏️ Редактор» правит конфиг **точечно** (source-preserving): меняется
только отредактированный диапазон YAML — комментарии, порядок, кавычки и
неизвестные ключи остаются как были; конфиг без правок экспортируется
байт-в-байт. Доступны: правка полей прокси/групп/провайдеров, переименование с
автоправкой всех ссылок, состав участников группы, цель правила, удаление с
показом зависимостей (ссылки в правилах нужно перенаправить вручную), добавление
прокси. Перед экспортом — «Статическая валидация: PASS/FAIL»; runtime-проверка
`mihomo -t` в браузере не выполняется. Экспорт — «Скопировать»/«Скачать» и
никогда не перезаписывает загруженный файл.

### Рабочая область графа

В Builder и Config Studio кнопка «⛶ Развернуть граф» открывает граф на размер окна; Escape возвращает обычный вид и фокус кнопки. В обычном виде высота меняется ползунком «Высота» или вертикальной ручкой контейнера; «Сбросить размер» возвращает автоматическую высоту. Fit учитывает новый размер. Zoom, pan и выбор узла сохраняются; «Весь граф» снимает фокус узла. Граф показывает CDG-зависимости, не наблюдаемый путь пакетов. Текстовая версия доступна под обычным графом.

### Список узлов runtime

В «Маршрутизация и DNS» включите «Показать серверы подписки», затем откройте импорт runtime. JSON можно загрузить локальным файлом. Длинные имена переносятся полностью; «ℹ только в runtime» означает отсутствие имени в browser preview, а не проверку пути пакетов. На узком экране метка переносится под имя. Список прокручивается и меняет высоту вертикальной ручкой; поиск меняет только отображение, checkbox — прежнюю модель исключений.

## Owner UX 2.1: быстрый путь

После профиля выберите автоматические белые списки и заполните основные / резервные серверы. Просмотр подписок, Device Model, фильтр и выбор узлов находятся рядом с вводом; получение списка остаётся явным действием. Общая закреплённая панель Build / Скачать / Copy / Сохранить / Загрузить доступна во всех пяти областях. Статус отличает сборку, актуальный YAML, изменённые настройки и ошибку; старый результат нельзя скопировать или скачать после изменения настроек. WG DNS и keepalive находятся рядом с файлами, выбор Web UI — рядом с переключателем и сохраняет значение при отключении.

## AWL и приоритеты

AWL и приоритетные группы серверов (Tiered) взаимоисключающие. При включении AWL подтвердите выключение активных Tiered/Per-Proxy; данные сохраняются. Отмена оставляет конфигурацию прежней. После выключения AWL режимы доступны, но включаются вручную. Для старых проектов такое же подтверждение применяется до Load, Undo и Restore. DPR SELECT остаётся доступным. Полная матрица: AUTO-WHITELIST.md.
