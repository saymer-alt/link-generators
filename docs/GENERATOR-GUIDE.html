Короткая инструкция по генератору

Короткая человеческая инструкция: как за пару минут получить рабочий конфиг. Совсем короткая версия с картинкой-сценариями — quick-start.html. Технические подробности — по ссылкам в конце.

1. Сначала выберите, где будет работать Mihomo

Первый вопрос наверху вкладки Builder: «🎯 Где будет работать Mihomo?»

🏠 Роутер / обычный TUN (Keenetic) — по умолчанию

Mihomo работает на домашнем роутере и поднимает TUN-интерфейс: весь трафик устройства идёт через него. Профиль включает TUN, MIPS stack, Mixed Port 7890 и Allow LAN — все параметры потом можно менять вручную.

🖥️ VPS — локальный Mihomo / SOCKS для Xray / 3X-UI

На VPS уже работает Xray/3X-UI (или другое приложение), которое отправляет трафик в Mihomo через 127.0.0.1:7890. Профиль выключает TUN, MIPS и Allow LAN (внешний доступ к 7890 не нужен) и оставляет только локальный SOCKS-вход. Схема: Xray/3X-UI → 127.0.0.1:7890 → Mihomo → proxy.

🌐 VPS Transparent Gateway (amnezia-mihomo-gateway)

Специальный сценарий: transparent-gateway с Linux policy routing / iptables / Docker / AmneziaWG. Генератор создаёт только Mihomo-часть (TUN tun-mihomo, DNS-перехват fake-ip, auto-route: false); Linux routing и firewall настраивает amnezia-mihomo-gateway. Allow LAN в этом профиле выключен принудительно (router-only опция) — gateway принимает трафик через TUN + policy routing, а не через LAN-listener. Для обычного VPS с Xray/3X-UI используйте предыдущий профиль.

🌐 Удалённый доступ к Web UI нескольких VPS (SSH local forwarding)

Controller/Web UI Mihomo в обоих VPS-профилях всегда слушает только 127.0.0.1:9090 — это фиксированный safety-контракт, порт на VPS не меняется. Конфликт нескольких одновременно открытых VPS решается на компьютере — разными локальными SSH/PuTTY forwarded-портами:

VPS-SE: local 9091 → remote 127.0.0.1:9090
VPS-EE: local 9092 → remote 127.0.0.1:9090
VPS-RU: local 9093 → remote 127.0.0.1:9090

Два разных понятия, которые не стоит путать:

  • remote port на VPS — порт, на котором Mihomo слушает на самом сервере (127.0.0.1:9090 на всех VPS, одинаково);
  • локальный forwarded-порт — порт на вашем компьютере, через который туннель (ssh -L 9091:127.0.0.1:9090, PuTTY «Local port») выпускает на Web UI (http://127.0.0.1:9091/ui/).

2. Входные данные

В поле «Основные прокси-ссылки / URL-подписки» вставьте:

  • обычные прокси-ссылки: vless://, trojan://, ss://, masque://… — напрямую;
  • ссылки на подписки (HTTP(S) URL) — при включённом режиме «URL-подписки»;
  • можно смешивать: подписка + обычные ссылки.

WARP-конфиги: вкладка ⚡ WARP MASQUE Links генерирует masque:// ссылки — кнопка «🚀 В Mihomo Builder» переносит их сюда. WireGuard/AmneziaWG — кнопка «📂 Загрузить .conf / .wg / .awg»: каждый файл станет отдельным WireGuard-прокси. Повторное нажатие добавляет файлы к уже загруженным (не заменяет!); загруженное видно списком с удалением по одному и кнопкой «🧹 Очистить все».

3. Основные переключатели

Переключатель Что делает
🛡️ TUN Interface Системный TUN: весь трафик устройства через Mihomo. Нужен на роутере; на VPS с локальным Xray — выключен.
⚡ MIPS stack Стек обработки TUN-трафика (не процессор!). По умолчанию MIPS; требует Mihomo ≥ 1.19.31, иначе gVisor.
🔌 Mixed Port 7890 Локальный HTTP+SOCKS вход Mihomo.
🌐 Allow LAN Доступ к Mihomo из локальной сети (добавляет bind-address: "*"). Доступно только в профиле «Роутер / обычный TUN»; в обоих VPS-профилях выключено принудительно.
🖥️ Web UI Веб-дашборд управления (MetaCubeXD) на порту 9090.
⚙ Расширенный TUN stack system/mixed — экспериментальные (внутри ADVANCED-секции); обычно достаточно MIPS/gVisor.

4. Подписки

Режим «📡 Использовать URL-подписки» превращает HTTP(S) ссылки в proxy-providers: Mihomo сам скачивает и обновляет списки узлов (раз в 12 часов + health-check).

  • 🚫 Exclude Filter — regexp по именам узлов подписки: совпавшие узлы исключаются. Важно: regexp сравнивается с фактическим именем узла. Латинский ru|russia не совпадёт с кириллическим «Россия» — для таких подписок пишите кириллический вариант (Россия|Москва). Семантика provider-level vs group-level: MIHOMO.md.
  • 📱 Device Model — необязательное понятное имя устройства (например: Keenetic Giga KN-1012, Windows-PC), которое панель подписки увидит как заголовок x-device-model в запросах списка серверов. Если пусто, в таких запросах используется служебное Saymer Link Generators Preview; на стабильный HWID значение не влияет.
  • 📋 Показать серверы подписки — opt-in toggle в блоке основных переключателей (по умолчанию выключен): при выключенном переключателе подписка браузером не запрашивается вовсе, provider-YAML собирается без обращения к сети. После включения список имён узлов запрашивается только по явной кнопке «Получить список»: поиск, «выбрать все»/«снять все», счётчики; отмеченные галочками узлы становятся точными исключениями и объединяются (OR) с ручным Exclude Filter. Запросы используют стабильный идентификатор генератора (HWID) — новое устройство не регистрируется на каждый Build. При CORS-проблемах используется проектный fallback-воркер (URL подписки при этом виден его инфраструктуре).
  • Некоторые панели (например, Geodema/Remnawave) требуют заголовок x-hwid — генератор добавляет его автоматически; без него панель может вернуть заглушку «App not supported» вместо списка узлов.

5. Политики по доменам (DPR)

Режим «🚦 Политики по доменам»: вы создаёте категории («AI», «YouTube»…) с списком доменов, и трафик на эти домены идёт через отдельную группу выхода. Остальной трафик идёт как раньше — завершающее правило MATCH,GLOBAL не меняется.

  • «➕ Добавить политику» → выберите шаблон (AI / YouTube / Telegram / Google / Direct) или впишите свои домены, по одному в строке. Голый домен = домен со всеми поддоменами; поддерживаются также DOMAIN-SUFFIX,…, CIDR, GEOSITE.
  • Правила указывают на группы, группы — на подписку: состав подписки меняется, правила пересобирать не нужно.
  • Нераспознанные строки пропускаются с предупреждением (конфиг всё равно собирается).
  • С «на каждый прокси» режим несовместим (выбранное не применяется).
  • Требуется Mihomo ≥ 1.19.27. Для pure-IP-клиентов (без доменов в запросе) на роутере домен «увидеть» сложнее — в профиле vps-gateway для этого есть автоматический пакет домен-детекта.

Подробно: POLICY-ROUTING.md.

Routing Inspector / Diagnostics

Внутри панели политик — сворачиваемый блок «DIAGNOSTICS — Routing Inspector / Diagnostics». Он работает по итоговому сгенерированному YAML (после Build) и только офлайн:

  • Routing order — человекочитаемый порядок правил: 1. AI → AI, … Всё остальное → GLOBAL; технические имена провайдеров не скрываются;
  • Проверка домена/IP — поле «Проверить домен или IP»: инспектор показывает победившее правило (номер + RAW), маршрут, альтернативные совпадения ниже по списку и объяснение «Mihomo применяет первое подходящее правило»;
  • Предупреждения — точные дубликаты правил и записей inline-провайдеров, перекрытые правила (DOMAIN-SUFFIX раньше уже покрывающего DOMAIN/более узкого SUFFIX), недостижимые правила после MATCH, неиспользуемые провайдеры, один домен в разных политиках (информация — порядок решает);
  • Rule Provider Explorer — вложенный сворачиваемый подраздел DIAGNOSTICS: read-only инвентарь всех rule-providers итогового конфига в порядке YAML. Сводка: провайдеры / используются / не используются / inline / внешние (только доказуемые http и file) / other-unknown (строка появляется, только если есть типы, отличные от inline/http/file) / отсутствующие ссылки. Карточка каждого провайдера: type, behavior, format, source и простые метаданные (url, path, interval, proxy, …), плюс все ссылки «used by: rule #N → TARGET». Провайдер без ссылок помечается «UNUSED», ссылка на несуществующий провайдер — «Referenced but missing» (проблема показывается, но не «чинится» автоматически). Для inline-провайдеров — число записей payload, локальный размер текста и поиск по подстроке (case-insensitive, только по уже доступному payload, без сохранения; показ ограничен первыми 500 записями с явной пометкой, счёт — по полному payload). Содержимое внешних (http/file) провайдеров браузером не загружается (никаких fetch/HEAD), MRS не декодируется — показываются только метаданные и «unavailable offline». Explorer ничего не меняет в YAML и ничего не сохраняет.

Честные ограничения: точно анализируются DOMAIN, DOMAIN-SUFFIX, DOMAIN-KEYWORD, MATCH и inline-провайдеры политик; DOMAIN-REGEX/DOMAIN-WILDCARD, GEOSITE/GEOIP, внешние (http/file) провайдеры и DNS-зависимые IP-правила возвращают UNKNOWN с причиной. Инспектор не заменяет диагностику самого Mihomo и ничего не меняет в конфиге; запросы никуда не отправляются и не сохраняются.

6. Автоматический режим белых списков (БС)

Включите «Автоматический режим белых списков» → появится второе поле. Верхнее поле — основные серверы, второе — резерв (то, что работает при блокировках). При недоступности основных выходов Mihomo сам переключится на резерв и вернётся обратно по плановой проверке. Переключение не мгновенное; «DIRECT» в цели не добавляется (если мертвы оба набора — трафика не будет). Опции «на каждый прокси» в этом режиме отключаются, а профиль развёртывания временно работает в router-совместимом варианте (ваш выбор профиля сохраняется и возвращается).

Подробно: AUTO-WHITELIST.md.

7. WARP/WireGuard через dialer-proxy

У каждого загруженного WG/AWG-профиля в карточке есть выбор «Подключение»:

  • Напрямую (по умолчанию) — обычный WireGuard-выход;
  • Через промежуточный proxy — туннель пойдёт через указанный proxy или группу («туннель в туннеле»): WARP подключается к Cloudflare из сети другого узла/страны. Имя таргета вводится тут же, у конкретного профиля; у другого профиля может быть свой таргет (или «Напрямую»).

Поля «Имя dialer-группы» / «Транзитные узлы» / «URL-подписки для dialer-группы» описывают состав группы; использует её или нет — решает каждая карточка отдельно. Новый профиль наследует заполненное глобальное поле как таргет по умолчанию (миграция старого сценария).

Два полевых факта:

  1. Промежуточный узел должен реально поддерживать UDP relay. Рабочие сайты/TCP через узел сами по себе не означают, что через него поднимется WireGuard/WARP. Проверяется только фактическим тестом.
  2. Переключение узла в dialer-группе — не мгновенная смена пути. Уже установленный WireGuard-хендшейк может держать старый transport path дольше 150 секунд. Для гарантированной смены пути нужен пересоздание outbound (reload конфига/перезапуск Mihomo). Смена colo Cloudflare — наблюдение, не гарантия: Cloudflare выбирает ingress сам.

8. ADVANCED Per-Proxy

Секция «ADVANCED — Отдельный вход на каждый прокси» по умолчанию свёрнута. Внутри: режим, создающий отдельный TUN/SOCKS-вход для каждого прокси. Для обычного использования не нужен. Раскрытие секции ничего не включает — включается только явный master-переключатель.
