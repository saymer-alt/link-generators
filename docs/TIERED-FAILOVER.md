# TIERED-FAILOVER — приоритетные эшелоны выходов (#148, v1.10)

Функция «🪜 Приоритетные эшелоны выходов» (Tiered Failover / Hierarchical
Provider Priority): упорядоченные эшелоны выходов со строгим приоритетом —
трафик идёт через первый эшелон, где есть живой выход; следующий эшелон
используется только когда весь предыдущий недоступен.

Отличие от обычного `url-test`: url-test выбирает быстрейшего из равноправных
участников; эшелоны — строгая иерархия приоритетов (например WARP → Резервные
выходы → Commercial → …; дефолтные имена новых эшелонов с v1.11 — «WARP» и
«Резервные выходы», ранее второй дефолт назывался «Personal» — существующие
пользовательские имена не мигрируются). Один и тот же выход в нескольких
эшелонах допустим (панель показывает warning-lint, это не build-ошибка).
Отличие от #149 Physical Multi-Hop: #149 — реальная цепочка
`клиент → VPS → VPS → WARP` (dialer/chan); здесь все выходы — прямые, а
«эшелон» — понятие приоритета выбора, не сетевого пути.

## Контракт

```text
ROOT «🪜 TIERED-AUTO» (fallback)
→ 🪜 1 <имя> (url-test | fallback)  ← первый живой эшелон
→ 🪜 2 <имя>
→ …
```

- Финальное правило `MATCH` направляет трафик в «🪜 TIERED-AUTO».
- `GLOBAL` получает root **первым участником** — ручное переключение в
  дашборде на другой выход остаётся возможным.
- Эшелон «пуст» (все участники мертвы) — runtime-условие, не build-ошибка.
- Пустой эшелон без участников, пустое имя, дубликат имени, неизвестный
  участник — **build-ошибка** с явным сообщением.

## Участники эшелона

Любой выход из текущей сборки: статические прокси, WG/AWG-профили,
провайдеры (`use:`). Участники хранятся только именами — никаких ключей/URL
в модели, trace или диагностике.

## Runtime semantics (доказано)

См. [research/TIERED-FAILOVER-RUNTIME.md](research/TIERED-FAILOVER-RUNTIME.md):
все сценарии (strict priority, частичный/полный отказ эшелона, failback,
nested fallback→fallback, provider tier, restart) — **RUNTIME-PROVEN** на
Mihomo 1.19.31 и 1.19.32 в детерминированном харнессе
(`tests/tiered-failover-runtime.cjs`). Health — HTTP(S)-пробы; поведение UDP
не заявляется (UNKNOWN).

Тайминги (наблюдения при interval 1s, не SLA): обнаружение+переключение
≈ 2–12 s, failback ≈ 1–1.7 s.

### Граница #2588

Воспроизводимый upstream-дефект: ручные controller-пробы группы
(`/group/:name/delay`) при длинном интервале могут «отравить» кэш alive
вложенной группы — root временно считает эшелон мёртвым, пока внутри есть
живой выход (см. `tests/mihomo-failover.cjs --nested-repro`). Сгенерированные
конфигурации ручных проб не содержат; при автоматических health-checks с
коротким интервалом дефект не наблюдался. Не маскируется генератором.

## Ручной override

`GLOBAL` сохраняет всех участников и REJECT: в дашборде можно вручную
переключить выход мимо эшелонов. Это осознанный manual-контракт, отдельный от
auto-иерархии; `store-selected` в сгенерированном конфиге не меняется.

## Пример

```yaml
GLOBAL → 🪜 TIERED-AUTO
🪜 TIERED-AUTO (fallback)
→ 🪜 1 WARP (url-test: [wg-a, wg-b])
→ 🪜 2 Commercial (fallback: [vps-se, geodema-1])
```
