# TIERED-FAILOVER — Приоритетные группы серверов (#148, v1.10)

Функция «🪜 Приоритетные группы серверов» (Tiered Failover / Hierarchical
Provider Priority): упорядоченные эшелоны выходов со строгим приоритетом —
трафик идёт через первый эшелон, где есть живой выход; следующий эшелон
используется только когда весь предыдущий недоступен.

Отличие от обычного `url-test`: url-test выбирает быстрейшего из равноправных
участников; эшелоны — строгая иерархия приоритетов (например WARP → Резервные
выходы → Commercial → …; новая карточка с Owner UX 2.1 называется «Приоритет 1», следующие — «Приоритет 2» и далее; существующие пользовательские имена не мигрируются). Один и тот же выход в нескольких
эшелонах допустим (панель показывает warning-lint, это не build-ошибка).
Отличие от #149 Physical Multi-Hop: #149 — реальная цепочка
`клиент → VPS → VPS → WARP` (dialer/chan); здесь все выходы — прямые, а
«эшелон» — понятие приоритета выбора, не сетевого пути.

## Контракт

```text
ROOT «🪜 TIERED-AUTO» (fallback)
→ 🪜 1 <имя> (url-test | fallback)  ← первый живой эшелон
→ 🪜 2 <имя>
→ …
```

- Финальное правило `MATCH` направляет трафик в «🪜 TIERED-AUTO».
- `GLOBAL` получает root **первым участником** — ручное переключение в
  дашборде на другой выход остаётся возможным.
- Эшелон «пуст» (все участники мертвы) — runtime-условие, не build-ошибка.
- Пустой эшелон без участников, пустое имя, дубликат имени, неизвестный
  участник — **build-ошибка** с явным сообщением.

## Участники эшелона

Любой выход из текущей сборки: статические прокси, WG/AWG-профили,
провайдеры (`use:`). Участники хранятся только именами — никаких ключей/URL
в модели, trace или диагностике.

## Runtime semantics (доказано)

См. [research/TIERED-FAILOVER-RUNTIME.md](research/TIERED-FAILOVER-RUNTIME.md):
все сценарии (strict priority, частичный/полный отказ эшелона, failback,
nested fallback→fallback, provider tier, restart) — **RUNTIME-PROVEN** на
Mihomo 1.19.31 и 1.19.32 в детерминированном харнессе
(`tests/tiered-failover-runtime.cjs`). Health — HTTP(S)-пробы; поведение UDP
не заявляется (UNKNOWN).

Тайминги (наблюдения при interval 1s, не SLA): обнаружение+переключение
≈ 2–12 s, failback ≈ 1–1.7 s.

### Граница #2588

Воспроизводимый upstream-дефект: ручные controller-пробы группы
(`/group/:name/delay`) при длинном интервале могут «отравить» кэш alive
вложенной группы — root временно считает эшелон мёртвым, пока внутри есть
живой выход (см. `tests/mihomo-failover.cjs --nested-repro`). Сгенерированные
конфигурации ручных проб не содержат; при автоматических health-checks с
коротким интервалом дефект не наблюдался. Не маскируется генератором.

## Ручной override

`GLOBAL` сохраняет всех участников и REJECT: в дашборде можно вручную
переключить выход мимо эшелонов. Это осознанный manual-контракт, отдельный от
auto-иерархии; `store-selected` в сгенерированном конфиге не меняется.

## Пример

```yaml
GLOBAL → 🪜 TIERED-AUTO
🪜 TIERED-AUTO (fallback)
→ 🪜 1 WARP (url-test: [wg-a, wg-b])
→ 🪜 2 Commercial (fallback: [vps-se, geodema-1])
```

## Название в интерфейсе UX 2.1

Функция отображается как «Приоритетные группы серверов». Tiered Failover остаётся техническим термином. Наборы проверяются по порядку; внутри — fastest (url-test) или ordered fallback. WARP не является обязательным первым набором. Диагностика отображает `[Приоритет]` вместо символа лестницы; настоящие имена `🪜 ...` и ссылки YAML сохраняются.

## Совместимость Owner UX 2.1

AWL и Tiered имеют разные контракты финального MATCH и выбираются по отдельности. При AWL включение требует подтверждения; сохранённые карточки свёрнуты в «Сохранено N групп приоритета», доступно раскрытие для просмотра. Редактирование заблокировано. AWL OFF разблокирует настройки, но не включает Tiered. Новый проект начинает с одной пустой группы «Приоритет 1»; «Добавить группу приоритета» создаёт «Приоритет 2», «Приоритет 3» и далее. Сохранённые имена, включая WARP, не мигрируют. Внутренние имена групп сохраняются. Пустую карточку заполните или удалите перед Build. Матрица и guards — AUTO-WHITELIST.md.

Между группами действует строгий приоритет первой доступной; восстановленная группа снова предпочтительна по результатам health-check. Внутри — url-test (измеренная задержка) или fallback (порядок участников). Это не физическая multi-hop цепочка, не обещание мгновенного переключения или сохранения действующих соединений.

### Owner Round 2: ввод участников

Выберите сервер в списке — подтверждённое изменение сразу добавляет его в текущую группу и возвращает select к приглашению. Дубликат не добавляется. ↑/↓ меняют порядок участников, × удаляет. Отдельной кнопки «Добавить выход» нет. Те же members сохраняются в проекте; старые проекты не мигрируются. Пустая группа остаётся ошибкой Build. Реестр доступен и без WG-файла. Смена focus/zoom/details не влияет на Build.

В человекочитаемых выводах используются «Приоритетные группы серверов», «1 группа / 2 группы / 5 групп», «Самый быстрый (url-test)» и «По порядку (fallback)». YAML имена `🪜 TIERED-AUTO` и `🪜 N <имя>` сохраняются. Диагностика маскирует исходные секреты до замены отображаемых обозначений. Новый Build очищает результат старой проверки Inspector.
