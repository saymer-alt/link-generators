VALIDATION — pre-copy валидатор Mihomo YAML

Автоматический режим белых списков (2026-09-15)

Контракт и точная структура YAML: AUTO-WHITELIST.md. UI передаёт опциональный fallbackInput; engine строит один плоский GLOBAL fallback с конечными узлами primary → fallback, без DIRECT и вложенных групп (#2588). Выключенный режим сохраняет прежний путь. Опции «на каждый прокси» и VPS исключаются независимо от скрытия UI; существующий validator проверяет итоговый YAML. Runtime требуется с поддержкой нового generic API.

Ревизия v1.19.31: MIPS для обычного и «TUN на каждый прокси» и AWG 3.1 fixture проходят структурную проверку. Runtime ограничивает выбор нового TUN stack; валидатор по-прежнему не проверяет глубоко tun.stack, AWG ranges или ключи. Это не mihomo -t. Сверка enum выявила отставание: в ядре 28 типов, в MIHOMO_PROXY_TYPES пока 27 (нет easytier). Генератор не создаёт EasyTier, изменение отложено в proposal. Ниже перечислены прежние проверки, а не утверждение о полном совпадении со всеми типами v1.19.31.

Полное описание слоя валидации (добавлен в f5ea0a3, 2026-09-08). Код — в index.html, секция // === MIHOMO BASIC VALIDATION ===. Решение о подходе утверждено владельцем 2026-09-08 (Вариант A+B по ТЗ исследования).

Почему появился валидатор

Реальный кейс: ссылка Mieru с опечаткой давала в готовом YAML

- name: Sweden Mieru
  type: mieru
  server: 5.175.236.6
  transport: TPC        # ← опечатка; mihomo требует ровно TCP или UDP

Mihomo отвергал такой конфиг уже после того, как пользователь копировал его на роутер. Поле приходит из пользовательской ссылки (web4core передаёт transport из URL как есть, дефолт TCP) — чинить только генерацию недостаточно, произвольный ввод может содержать любой мусор. Поэтому проверяется итоговый YAML после buildFromRequest() и всех патчей, а не исходные ссылки.

Почему это не настоящий Mihomo и не WASM (архитектурное ограничение)

Исследование 2026-09-08 (факты, не догадки):

  • официальные релизы MetaCubeX/mihomo не содержат wasm/wasip1/js-таргетов (v1.19.30 — 128 ассетов, ноль browser-сборок);
  • config.Parse неотделим от ядра (adapter, listener, dns, tunnel); обязательная зависимость quic-go под WASM собирается только как wasip1 с host-сокетами — браузеры UDP не предоставляют;
  • официальный дашборд metacubexd валидирует только через живое ядро по REST API — статической странице нечем;
  • готового браузерного runtime с настоящим кодом mihomo не существует; форк «только парсера» невозможен, а полный форк — вечное обслуживание.

Вывод: настоящий mihomo -t в браузере нереализуем. Выбранный вариант — локальный структурный validator, проверяющий только то, что mihomo гарантированно отвергнет, с честной формулировкой результата (никаких «✅ Mihomo config проверен»). Это архитектурное ограничение, а не временная недоделка.

Этот validator не является реализацией mihomo -t и не гарантирует, что Mihomo примет конфигурацию. Он структурный: ловит уверенные ошибки до копирования, но пропущенные им конфиги могут быть отвергнуты ядром. Авторитетная проверка — на целевой машине:

mihomo -t -f /opt/etc/mihomo/config.yaml

Если browser validator показывает VALID, а настоящий Mihomo отвечает ошибкой, это не повод добавлять правило наугад. Для воспроизводимого разбора нужны полный сгенерированный YAML и полный stdout/stderr mihomo -t на том же файле. Только после этого ошибка либо превращается в доказуемое структурное правило + regression fixture, либо фиксируется как граница browser validation, если без ядра/окружения её надёжно определить нельзя.

Контракт поддержки после Build

Сгенерированный YAML можно изменять вручную — проект это не запрещает. Но после любого ручного добавления, удаления или изменения строк, значений, отступов либо структуры файл считается пользовательской конфигурацией.

Результат browser validator и гарантии генератора относятся только к YAML, полученному непосредственно после ⚡ Build Config без последующих изменений. После ручного редактирования пользователь самостоятельно отвечает за внесённые изменения и обязан проверить итоговый файл на целевой версии Mihomo:

mihomo -t -f /path/to/config.yaml

Сообщение об ошибке генератора или validator gap принимается к воспроизводимому разбору только если ошибка повторяется на неизменённом YAML непосредственно из генератора. Evidence должен содержать этот YAML и полный stdout/stderr mihomo -t, выполненного именно на нём. Ошибка, возникшая только после ручного изменения YAML, сама по себе не является доказательством дефекта генератора или browser validator.

Архитектура

⚡ Build Config
      ↓
web4core.buildFromRequest() → YAML-строка
      ↓  пост-обработка страницы: injectWgDns → allow-lan патч
финальный YAML (= содержимое #mihomoOutput)
      ↓
runMihomoValidation(yaml)     [async: VALIDATING отрисован ~30 мс]
      ↓
validateMihomoYaml(yaml)      [чистая функция: jsyaml.load + структурные проверки]
      ↓
{ status: VALID|INVALID, errors[], warnings[] }
      ↓
статус-бокс + блокировка/разрешение Copy YAML

Валидатор — чистая функция над строкой: не пишет в DOM, не влияет на генерацию, сетевых вызовов нет. Динамический HTML статус-бокса проходит escapeHtml() (значения полей — пользовательский ввод).

State machine

             ┌────────────┐
  загрузка/  │  NOT_BUILT │ ←— любое input/change событие на документе
  ошибка     │            │     (поля, чекбоксы, select, файлы, WG DNS)
  сборки     └─────┬──────┘
                  │ Build Config (yaml получен)
                  ▼
             ┌────────────┐
             │ VALIDATING │  «⏳ Базовая проверка конфигурации...»
             └─────┬──────┘
        ошибок нет │          │ есть ERROR
                   ▼          ▼
             ┌────────┐   ┌─────────┐
             │  VALID │   │ INVALID │   Copy: включена / заблокирована
             └────────┘   └─────────┘
  • Generation counter (mihomoValidationSeq): инкрементируется при старте проверки и при каждом сбросе. Финальный статус применяется только если поколение не изменилось — сброс во время асинхронного окна не может быть перезаписан поздним VALID (защита от race), а «хвост» старой проверки после второго Build не перезаписывает новую.
  • Сброс: document-level capture-слушатели input + change — любое изменение любого элемента страницы инвалидирует результат. Программные записи .value/textContent события не создают, поэтому собственные записи страницы ложных сбросов не дают.
  • Copy gating — двойной рубеж: #copyYamlBtn.disabled = (state !== 'VALID') и guard в начале copyMihomo() (toast «Копирование заблокировано…», выход до обращения к clipboard). Silently-success невозможен.

Формулировки результата — ровно как утверждено владельцем:

  • ⚠️ Базовая проверка пройдена. Это не эквивалент проверки mihomo -t.; интерфейс также показывает пример финальной команды и требования к evidence для случаев, когда ядро отклоняет YAML
  • ❌ Ошибка базовой проверки + блоки Proxy: … / Field: … / Value: … / Ошибка: …
    • «Исправьте конфигурацию и выполните ⚡ Build Config снова.»

ERROR — фактические проверки (блокируют Copy)

Каждая сверена с исходниками mihomo (Alpha, линия v1.19.x) — «уверенная» означает «ядро это отвергнет»:

# Проверка Обоснование из mihomo
1 YAML не парсится (jsyaml.load бросает) —
2 Корень YAML — не словарь decode конфига
3 Скалярные порты port/socks-port/mixed-port/redir-port/tproxy-port — не целые 1–65535 диапазон портов
4 dns/tun/proxy-providers/rule-providers — не словари; rules/listeners/inbounds — не списки; правило — не непустая строка decode секций
5 proxies[i]: name отсутствует/пустое обязательное поле
6 Дубликат имени прокси config.go: «proxy … is the duplicate name»
7 type отсутствует или не из списка 27 типов (MIHOMO_PROXY_TYPES) adapter/parser.go: unsupport proxy type
8 Для 19 server-based типов: server отсутствует/пустое обязательное поле (для direct/reject/dns/rematch/openvpn/tailscale/zerotier/wireguard не требуется — сознательно не строже ядра)
9 port — не целое 1–65535 (те же 19 типов) decode int + диапазон
10 mieru: transport ∉ {TCP, UDP} (в т.ч. кейс TPC) adapter/outbound/mieru.go: «transport must be TCP or UDP»
10a mieru с непустым port-range: (а) одновременно задан port ≠ 0; (б) port-range — не строка вида N-M; (в) границы вне 1–65535 или начало > конец. При наличии port-range поле port НЕ требуется — правило 9 для mieru не применяется adapter/outbound/mieru.go: PortRange string (proxy:"port-range,omitempty"), формат %d-%d, взаимоисключимость с port («port and port-range cannot be set at the same time»), границы 1–65535, begin <= end; рантайм при заданном server_ports пишет port-range и НЕ пишет port
11 proxy-groups[i]: name/type отсутствуют; тип не из {select, url-test, fallback, load-balance, relay} adapter/outboundgroup/parser.go
12 Дубликат имени группы; имя группы == имени прокси-элемента не блокируется (см. WARNING) config.go: «the duplicate name»
13 Ссылка в group.proxies не разрешается в прокси/группу/builtin (DIRECT, REJECT, REJECT-DROP, PASS, COMPATIBLE, GLOBAL); forward-ссылки на группы разрешены проверка резолвера групп
14 listeners/inbounds: элемент — не словарь, port вне 1–65535, дубликат name config.go: listener duplicate name

Списки типов — точные копии switch-веток исходников; при обновлении целевой версии mihomo их стоит сверить заново (MIHOMO_PROXY_TYPES, MIHOMO_GROUP_TYPES в index.html).

WARNING — предупреждения (Copy не блокируют)

  • dialer-циклы (ERROR) и dynamic provider-ветви (WARNING) — анализ через единый dependency-graph рантайма web4core.analyzeDialerGraph: см. «Конфигурация Mihomo как ориентированный граф» в MIHOMO.md. Цикл (маршрут, возвращающийся к исходному outbound) — ERROR с полным путём; провайдер dialer-группы без override.dialer-proxy — WARNING dynamic/unknown (статически цикл не доказан и не исключён, содержимое подписки неизвестно; UDP-совместимость не проверяется).
  • имя группы совпадает с именем прокси (пересечение пространств имён);
  • у группы пустой список proxies;
  • Compatibility-требования (например, MIPS/AWG/Modern REALITY) вынесены в отдельный неблокирующий блок после Build и не считаются warning валидатора.

Deliberate omissions — что сознательно НЕ проверяется

Принцип: ложная блокировка валидного конфига хуже пропущенной ошибки — валидатор не должен быть строже эталона.

  • Неизвестные/лишние поля — mihomo декодирует YAML без KnownFields, незнакомые поля игнорирует; флагать их значило бы блокировать то, что ядро примет.
  • Глубокая проверка DNS (dns:), tun, sniffer и т.п. — только форма секции.
  • Правила rules — только «непустая строка»; синтаксис правил не парсится.
  • url-test URL / expected-status / интервалы — не проверяются.
  • AWG-специфичные поля (amnezia-wg-option) — passthrough не валидируется, чтобы не сломать AWG 3.1 (свежая функциональность генератора); проверяется регресс-тестом, что AWG 3.1 конфиг проходит валидацию.
  • Семантика паролей/ключей/UUID — не проверяется.

Как это тестируется

Юнит-матрица (42 кейса) и браузерные e2e сценарии — TESTING.md. Регрессионный минимум: transport: TPC → INVALID + Copy заблокирована; TCP → VALID; AWG 3.1 → VALID; изменение входа сбрасывает VALID.
